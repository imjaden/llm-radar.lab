## 一、loop.md 是什么

`requirements.md` 是项目根目录下的迭代需求清单。当你有一批功能要增/改/删时，写在 `requirements.md` 里，AI 读取后逐条实现。

### 定位

```
不是: 详细的技术设计文档（那是 documents/ 下各 spec 的职责）
不是: 随意的聊天记录（边聊边改，没有结构化）
是:   结构化的需求清单，每条独立可验收
```

### 为什么不用直接对话

| 方式 | 适合 | 不适合 |
|------|------|--------|
| 直接对话 | 1-2 条简单需求，边聊边改 | 批量需求、涉及多个文件的改动 |
| requirements.md | 3 条以上的批量需求、涉及多个文件的改动 | 需要来回确认的模糊需求 |

如果你不确定某条需求怎么描述才清晰，先在聊天里讨论清楚，确认后再写入 loop.md。

## 二、文件模板

```markdown
# 迭代需求: <简短标题>

## 涉及文件
- llm-radar-collector.py (函数名)
- llm-radar-mcp-server.py (如果涉及)
- data/snapshot.json (数据结构变化)

---

## Bug 修复

### 1. [简短标题]

场景：你遇到了什么问题？什么操作触发的？
期望：应该发生什么？
实际：实际发生了什么？

---

## 功能新增

### 2. [简短标题]

场景：为什么需要这个功能？解决了什么痛点？
行为：
  - 在哪个文件/流程中改
  - 输入是什么，输出是什么
  - 触发条件是什么
验收：你怎么手动或通过测试验证？观察到什么就算通过？

### 3. [同上结构]

---

## 强调

1. 每条需求独立 commit（一条 commit 对应一个功能点）
2. 实现后运行 tests/ 下的测试验证
3. 验证无误后 commit，但不 push（review 通过后自动 push）
4. 验收不通过时，AI 修复后重新验证
```

## 三、编写原则

### 原则 1：每条需求可独立测试

同一轮迭代中的需求应该互不依赖。如果需求 B 依赖需求 A 先完成，分两轮写。

```
❌ 混在一起:
  1. 添加新数据源 qbitai
  2. qbitai 数据格式转换

✅ 分开:
  第 1 轮: 1. 添加新数据源 qbitai
  第 2 轮: 1. qbitai 数据格式转换（依赖第 1 轮的 fetch 接口）
```

### 原则 2：引用现有 documents/ 中的术语

不要自创名词，使用现有文档中已有的术语。

```
❌ "采集器里的处理函数改一下"
✅ "修改 llm-radar-collector.py 的 _extract() 方法中的 LLM prompt（见 documents/data-flow-v1.0.md §3.2）"
```

### 原则 3：场景优先，方案次之

描述「用户遇到了什么问题」，而不是「我觉得应该改哪行代码」。

```
❌ "在 _verify() 的 issues.append 后面加一个 if"
✅ "当新鲜度检查发现所有事件都超过 7 天时，应该跳过 push 并记录原因"
```

建议比例：**70% 场景描述 + 30% 行为期望**。

### 原则 4：验收标准要有可观测行为

验收标准不应该依赖你「看代码」来判断，而应该是你**检查输出或运行测试**就能确认的。

```
❌ "代码逻辑正确"
✅ "运行 python3 tests/test_collector.py → 测试全部通过"
❌ "数据存对了"
✅ "cat data/snapshot.json | jq '.entities | length' > 之前的值"
```

### 原则 5：区分 Bug 和 Feature

Bug 修复和功能新增放在不同章节。AI 处理 Bug 时不做功能增强，处理功能时不做 Bug 修复。

```
✅
## Bug 修复
### 1. 数据源 qbitai 超时不重试
### 2. 合并时重复实体未去重

## 功能新增
### 3. 新增 RSS 数据源支持
### 4. 添加数据新鲜度告警
```

## 四、常见反模式

### 反模式 1：需求外溢

```
需求: "新增 RSS 数据源。顺便把采集间隔改成 4 小时。"
```

➡ 拆成两条独立需求。间隔调整可能涉及运维配置，需要单独评估。

### 反模式 2：只写行为，不写场景

```
需求: "_merge() 里加一个按热度排序的逻辑"
```

➡ 缺少场景。你可能想「热点事件优先显示」，而不是真的在意 merge 函数本身。

### 反模式 3：验收标准模糊

```
需求: "性能更好"
```

➡ 无法验证。改为："一次完整采集（7 源 fetch + LLM extract + merge）耗时从 120s 降到 90s 以内"。

### 反模式 4：一个需求里塞了多个改动

```
需求: "添加新数据源、修复去重 bug、优化提取 prompt"
```

➡ 三条独立需求。一条不满足时其他两条不需要回退。

### 反模式 5：不更新 documents/ 文档

如果新功能改变了已有的约束（如新增数据源字段、改变合并规则），在 requirements.md 末尾注明：

```
## 同步更新
- documents/data-flow-v1.0.md §2.3: 新增字段 "rss_url"
- documents/features.md: 追加 RSS 数据源
```

## 五、与 AI 的协作流程

```
你：写完 requirements.md → "loop.md 已更新，执行"
            ↓
AI：读取 loop.md，逐条理解
            ↓
AI：对每一条需求，用自己的话复述一遍 + 验收方案
   "需求 1 的理解：在 collector 里新增 RSS 源支持...
    验收计划：运行测试，检查 RSS 数据是否被打标。对吗？"
            ↓
你：确认或修正 → "对，执行" / "不对，应该是..."
            ↓
AI：实现 → 测试 → commit（不 push）
            ↓
AI：打印实现清单和验证结果到 feature.md
            ↓
你：验收 → 通过则等 cron 自动 review / 不通过则追加修复需求
```

关键节点在 **AI 复述理解** 那一步。花 30 秒让 AI 复述一遍，省去后面 10 分钟的来回修改。

## 六、每次迭代的默认约束

以下约束适用于每一轮 requirements.md 的执行，无需在需求中重复写明：

### 6.1 实现后必须测试验证

每条需求实现后，AI 必须自行验证功能是否符合验收标准。验证方式：

```
- 代码改动：运行 tests/ 下的对应测试
- 数据改动：运行采集器并检查 snapshot.json 输出
- 交互改动：运行 MCP 测试脚本
```

不能以「代码看起来没问题」作为验证结论。

### 6.2 验证通过后打印结果

每轮执行完毕后，AI 必须将实现清单写入 `features.md`：

```markdown
### 实现功能清单

| # | 需求 | 状态 | 验证方式 |
|---|------|------|---------|
| 1 | 新增 RSS 数据源 | ✅ | tests/test_rss.py 全部通过 |
| 2 | 去重逻辑修复 | ✅ | 重复数据不再合并 |

### 验证结果

| 检查项 | 结果 |
|--------|------|
| 测试用例全部通过 | ✅ 15/15 |
| 运行 collector 一次 | ✅ 新数据正常 |
```

### 6.3 验证测试用例

每轮实现完成后，在打印功能清单之前，必须先执行以下步骤：

1. **检查测试完整性**：确认 `tests/` 下是否包含本轮新增/修改功能的对应测试用例
2. **补全缺失用例**：如果新功能没有对应测试，补充
3. **验证全部通过**：执行测试，确认所有用例通过

测试不通过时不得 commit。

### 6.4 Commit 但不 Push

每轮修改完成后，AI 需要：

1. `git add -A`（只添加本轮改动的文件）
2. `git commit -m "type@llm-radar: 简短的变更描述"`
3. **不执行 `git push`**

Commit message 格式：

| type | 适用 |
|------|------|
| `add` | 新增功能 |
| `fixed` | 修复 Bug |
| `optimized` | 优化改进 |
| `refactor` | 重构 |
| `docs` | 文档 |
| `test` | 测试 |
| `chore` | 杂项 |

## 七、验证清单

提交 requirements.md 之前，逐项检查：

- [ ] 每条需求独立编号
- [ ] 每条需求有场景描述
- [ ] 每条需求有可观测的验收标准
- [ ] Bug 和 Feature 分章节
- [ ] 涉及文件列在开头
- [ ] 术语与现有 documents/ 一致
- [ ] 没有「顺便改一下」的外溢需求
- [ ] 如有约束变化，标注需同步更新对应 documents/
- [ ] 本轮需求互不依赖（可独立 commit）
